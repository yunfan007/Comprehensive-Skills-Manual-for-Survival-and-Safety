# 项目内部参考文档编写及开发通用要求

> 本文档适用于本仓库所有内部参考文档的编写、维护、审查与发布流程。所有贡献者须遵守以下要求。

---

## 一、文档分级与可见性

### 1.1 分级标准

| 级别 | 标识 | 可见范围 | 内容示例 |
|------|------|----------|----------|
| **公开** | `[PUBLIC]` | 仓库公开内容 | 项目概述、通用技术说明、免责声明、使用指引 |
| **内部** | `[INTERNAL]` | 开发组成员 | 完整技术细节、操作流程、未定稿章节 |
| **受限** | `[RESTRICTED]` | 核心开发组 | 高敏感技术参数、风险操作相关附录 |

### 1.2 操作要求

- 文档头部须标注级别标识（如 `[INTERNAL]`）
- 不同级别内容须分文件存放，路径命名须体现分级
- `[RESTRICTED]` 级内容**不得**提交至公共仓库
- 引用外部资料须注明出处并评估版权状态

## 二、版本与变更管理

### 2.1 文件头部元数据

每个 `.md` 文件须在顶部包含以下元数据（YAML格式）：

```yaml
---
title: 文档标题
version: x.y.z
status: 草稿 | 审查中 | 已发布 | 已归档
last_review: YYYY-MM-DD
owner: 负责成员代号
---
```

### 2.2 变更记录

- 每次实质性修改须在文件底部追加变更记录：

```markdown
## 变更记录
| 日期 | 版本 | 修改人 | 修改摘要 |
|------|------|--------|----------|
| YYYY-MM-DD | x.y.z | [代号] | [简述] |
```

- 变更须通过 PR 或审批流程合并
- 归档文档版本冻结，不可修改，新版本另行创建

## 三、编写规范

### 3.1 语言与风格

- 使用**中文撰写**，技术术语可保留英文原文，首次出现须附中文解释
- **指令性表述**：使用“应当”“不得”“必须”“禁止”等明确词汇
- **描述性表述**：使用平实语言，避免文学化修饰
- 各章节统一采用“编—章—节—条”四级编号体系

### 3.2 技术内容要求

- 任何操作描述须包含**前置条件、操作步骤、安全提示、预期结果**四个部分
- 涉及风险操作须在对应章节添加警告框：

> ⚠️ 本操作仅在 [具体条件] 下方可执行，执行前须确认 [安全条件]。

- **禁止**在内部参考文档中使用模糊表述（如“可尝试”、“据说”、“有人建议”）
- 所有数据和参数须注明来源或验证状态（已验证 / 待验证 / 文献参考）

## 四、审查与审批流程

| 阶段 | 内容 | 负责角色 |
|------|------|----------|
| 初稿 | 完成基础内容编写 | 编写组成员 |
| 技术审查 | 核实操作逻辑、参数准确性 | 技术负责人/战术组员 |
| 法律审查 | 评估法律风险，标注红线条款 | 法理与伦理委员 |
| 定稿 | 综合意见完成修订 | 项目负责人 |
| 发布 | 依照分级放入对应目录并记录 | 排版/发布负责人 |

> 审查过程中的修改意见须以可追溯的形式记录（如 PR 评论、审查记录表）。

## 五、安全与合规红线

### 5.1 绝对禁止内容（不写入任何级别文档）

- 针对特定国家、机构、团体或个人的攻击性、煽动性内容
- 涉及现实暴力、非法活动的操作指导
- 未经验证的人体伤害性技术
- 明显违反所在国法律的内容

### 5.2 敏感内容管控

- 涉及**自制设备、化学制剂、爆破相关**的内容，仅可存在于 `[RESTRICTED]` 级文档中
- `[RESTRICTED]` 级文档须额外附带：《敏感内容操作安全协议》（单独文件）
- 所有敏感内容须标注：“本条目信息仅用于【具体限制条件】，不构成操作建议”

## 六、协作与行为准则

### 6.1 提交与合并

- 所有提交须附清晰的提交信息（`git commit -m`），说明修改范围和原因
- 公开分支的合并须至少经两人评审
- 内部分支的合并由项目负责人批准

### 6.2 保密义务

- 开发组成员不得在公开渠道（包括但不限于社交媒体、公开论坛、群聊）讨论或传播内部与受限级文档内容
- 未经授权向团队外人员展示或交付内部文档的，依团队内部规则处理
- 邀请新成员须经现有成员一致同意，并同步更新开发组名单

### 6.3 贡献者确认

- 所有开发组成员须在 `CONTRIBUTORS.md` 中记录代号与主要职责
- 新成员加入前应完成基础内容熟悉（至少阅读公开级别全部文档）

## 七、仓库目录结构（建议）

```
/repo-root
├── README.md                 # 项目主页（公开）
├── CONTRIBUTORS.md           # 开发组名单（内部）
├── docs/
│   ├── public/               # 可公开发布的文档
│   ├── internal/             # 开发组内部可见文档
│   ├── restricted/           # 核心组限阅（**不提交至公共仓库，仅本地或私有存储**）
│   └── templates/            # 文档模板
├── guidelines/
│   └── DOC_REQUIREMENTS.md   # 本文档（内部）
└── archive/                  # 已归档的历史版本
```

## 八、附录：文档完成状态标记

在目录或文件元数据中使用以下标记，便于状态追踪：

| 标记 | 含义 |
|------|------|
| `[DRAFT]` | 草稿，尚未审查 |
| `[WIP]` | 编写中，随时变动 |
| `[REVIEW]` | 审查中 |
| `[FINAL]` | 已定稿，可发布 |
| `[ARCHIVED]` | 已归档，不再修改 |
| `[OBSOLETE]` | 已废弃，仅作历史参考 |
